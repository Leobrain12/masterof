# Решения — почему так, а не иначе

Неочевидные развилки, задокументированные в момент принятия, пока контекст свежий. Не история изменений (для этого есть git) — только те решения, которые могли бы быть приняты иначе и стоило объяснить, почему выбрали именно так.

## Без Telegram SDK

Вместо `irazasyed/telegram-bot-sdk` или аналога — собственный `TelegramClient` поверх `Http::post`. Причина: нет возможности протестировать код вживую против реального Bot API (токена ещё не было на момент написания), а значит риск наугад промахнуться мимо точного метода/сигнатуры чужого пакета выше, чем цена написать 5 методов (`sendMessage`, `answerCallbackQuery`, `setWebhook`, `deleteWebhook`, `getWebhookInfo`, `getMe`) самому. Telegram Bot API — плоский HTTP/JSON, обёртка почти не экономит код.

## Docker вместо локального PHP

`CLAUDE.md`, который принёс стандартный Laravel-инсталлятор, просил поставить PHP/Composer локально + `laravel/boost`. Решили не ставить: Docker Compose и так даёт рабочее окружение, задача явно предполагала deploy через docker-compose (пункт чек-листа "Фаза 00"), а Boost внутри уже идущей сессии новых инструментов не даёт (он больше для будущих сессий/других IDE). Все `artisan`-команды идут через `docker compose exec app`.

## PHPUnit env vs $_SERVER

`docker-compose.yml` изначально передавал `.env` в контейнер через `env_file`. Из-за этого переменные (`APP_ENV=local`, `DB_CONNECTION=pgsql` и т.д.) оказывались в `$_SERVER` ещё до старта PHPUnit, а `phpdotenv`/Laravel читают `$_SERVER` как "уже установлено" и не дают PHPUnit переопределить их — даже с `force="true"` в `phpunit.xml`, потому что тот `force` управляет только `getenv()`/`$_ENV`, а не `$_SERVER`. Итог: `RefreshDatabase` в тестах реально дропал таблицы в dev-базе Postgres. Убрали `env_file` из `docker-compose.yml` (Laravel и так читает `.env` с диска через смонтированный volume), оставили `force="true"` в `phpunit.xml` как defence in depth.

## master:add без создания ADMIN/SUPERADMIN

Аудит после Фазы 07 нашёл: завести нового мастера можно было только руками через `tinker`/SQL — не задокументировано и не покрыто командой. Добавили `master:add` (см. README#Добавление-мастера), но только для роли MASTER. Заводить ADMIN/SUPERADMIN той же командой не стали: это редкое, более доверенное действие (полный доступ к системе), для которого ручной `tinker` — не пробел, а разумный порог трения. `--appliance` в команде обязателен (не опционален), потому что `MasterMatcher` фильтрует специализацию жёстко (см. [[Фаза 01 — Заказы]]) — мастер без неё был бы молча невидим для подбора, не мягким ограничением, а фактической потерей мастера.

## Номер заказа без DB sequence

Изначально `orders.number` был `bigint` с дефолтом от Postgres `SEQUENCE` — красиво и правильно для прода, но `CREATE SEQUENCE` не существует в SQLite, на котором гоняются тесты. Не стали городить два разных пути для миграции (branch по `DB::getDriverName()`), просто перенесли генерацию в `Order::booted()` (`creating`-хук, `max(number) + 1`). Плата — теоретическая гонка при одновременном создании двух заказов (никогда не проверяли на реальной конкурентной нагрузке); при соло-разработке и небольшом потоке заказов это осознанно приемлемый риск, а не забытый баг. Если станет проблемой — вернуть Postgres-sequence с миграцией, специфичной для окружения.

## PendingInput как общий примитив

Причина отказа мастера "Другое" (ТЗ п.22) требует одного свободного текстового ответа вне сценария создания заявки. Вместо специальной таблицы под этот один случай — завели `pending_inputs` (`user_id` unique, `kind`, JSON `payload`, `expires_at`) как переиспользуемый примитив "жду один ответ по такому-то поводу". Оправдалось уже в Фазе 02 (шаги согласования цены). `order_drafts` — отдельная сущность, не унифицирована с `pending_inputs`, потому что там принципиально другая форма: заранее известная последовательность из 12+ шагов с типизированным enum, а не одноразовое ожидание.

## DateSlotPicker — вынесено на третьем использовании

Выбор "дата → слот" писался с нуля дважды: в `OrderDraftFlow` (Фаза 01, создание заявки) и в `OrderRescheduleFlow` (Фаза 02, перенос). Оба раза — осознанное дублирование (разные контексты, риск регрессии в уже протестированном коде). На третий раз (Фаза 03, планирование повторного визита в `OrderVisitFlow`) вынесли общий `DateSlotPicker`: рендер шагов + разбор "ДД.ММ" в одном месте. `OrderRescheduleFlow` отрефакторили на него, `OrderDraftFlow` — оставили как есть (не стали трогать проверенный код ради унификации). Дополнительный повод: именно в разборе даты жил баг с `Carbon::createFromFormat()` (см. [[Фаза 02 — Полевой цикл#Пойманные баги по пути]]) — одна точка вместо трёх снижает риск, что фикс в будущем попадёт не везде.

## Перенос не меняет статус

ТЗ описывает `RESCHEDULED` как статус в общем списке, но граф переходов (п.15) даёт его двусмысленно ("ACCEPTED → ON_THE_WAY → RESCHEDULED"). Решили: перенос — это событие (меняются `visit_date`/`time_slot_label`), а не "заказ повис в состоянии RESCHEDULED, дальше берём его оттуда" — потому что дальше явно неоткуда брать (переход из RESCHEDULED никуда не описан). Решение: менять напрямую полями заказа + писать отдельную запись в `order_status_histories` с `old_status == new_status` и комментарием-описанием переноса, в обход `OrderStatusMachine::transition()` (это не транзиция состояния). `OrderStatus::RESCHEDULED` остаётся в enum как задокументированный неиспользуемый кейс — на случай, если позже понадобится показывать перенесённые заказы отдельным фильтром.
