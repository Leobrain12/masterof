# Решения — почему так, а не иначе

Неочевидные развилки, задокументированные в момент принятия, пока контекст свежий. Не история изменений (для этого есть git) — только те решения, которые могли бы быть приняты иначе и стоило объяснить, почему выбрали именно так.

## Без Telegram SDK

Вместо `irazasyed/telegram-bot-sdk` или аналога — собственный `TelegramClient` поверх `Http::post`. Причина: нет возможности протестировать код вживую против реального Bot API (токена ещё не было на момент написания), а значит риск наугад промахнуться мимо точного метода/сигнатуры чужого пакета выше, чем цена написать 5 методов (`sendMessage`, `answerCallbackQuery`, `setWebhook`, `deleteWebhook`, `getWebhookInfo`, `getMe`) самому. Telegram Bot API — плоский HTTP/JSON, обёртка почти не экономит код.

## Docker вместо локального PHP

`CLAUDE.md`, который принёс стандартный Laravel-инсталлятор, просил поставить PHP/Composer локально + `laravel/boost`. Решили не ставить: Docker Compose и так даёт рабочее окружение, задача явно предполагала deploy через docker-compose (пункт чек-листа "Фаза 00"), а Boost внутри уже идущей сессии новых инструментов не даёт (он больше для будущих сессий/других IDE). Все `artisan`-команды идут через `docker compose exec app`.

## PHPUnit env vs $_SERVER

`docker-compose.yml` изначально передавал `.env` в контейнер через `env_file`. Из-за этого переменные (`APP_ENV=local`, `DB_CONNECTION=pgsql` и т.д.) оказывались в `$_SERVER` ещё до старта PHPUnit, а `phpdotenv`/Laravel читают `$_SERVER` как "уже установлено" и не дают PHPUnit переопределить их — даже с `force="true"` в `phpunit.xml`, потому что тот `force` управляет только `getenv()`/`$_ENV`, а не `$_SERVER`. Итог: `RefreshDatabase` в тестах реально дропал таблицы в dev-базе Postgres. Убрали `env_file` из `docker-compose.yml` (Laravel и так читает `.env` с диска через смонтированный volume), оставили `force="true"` в `phpunit.xml` как defence in depth.

## master:add без создания ADMIN/SUPERADMIN

Аудит после Фазы 07 нашёл: завести нового мастера можно было только руками через `tinker`/SQL — не задокументировано и не покрыто командой. Добавили `master:add` (см. README#Добавление-мастера), но только для роли MASTER. Заводить ADMIN/SUPERADMIN той же командой не стали: это редкое, более доверенное действие (полный доступ к системе), для которого ручной `tinker` — не пробел, а разумный порог трения. `--appliance` в команде обязателен (не опционален), потому что `MasterMatcher` фильтрует специализацию жёстко (см. [[Фаза 01 — Заказы]]) — мастер без неё был бы молча невидим для подбора, не мягким ограничением, а фактической потерей мастера.

## Rate limiting — throttle до аутентификации, не после

`throttle:telegram-webhook`/`throttle:internal-api` в `routes/api.php` стоят первым элементом массива middleware, перед `VerifyTelegramWebhookSecret`/`VerifyInternalApiKey`. Осознанно: цель — не пустить объём запросов дальше по пайплайну (включая работу самой проверки и, если бы она прошла, обработку апдейта/транзакции), а не только считать успешные. Побочный эффект — неавторизованный флуд тоже расходует лимит того, кто флудит, а не легитимного клиента: у `internal-api` лимитер ключуется по `X-Internal-Api-Key`, а не по IP, поэтому разные клиенты (пока только будущая CRM, но их может стать больше) не делят один бюджет просто из-за общего прокси/NAT.

## CRM sync не полагается на асинхронность очереди

`SyncOrderToCrm::dispatch()` в проде (Redis) неблокирующий и сам по себе не бросает исключений — казалось бы, п.87 ("CRM не SPOF") соблюдается просто по природе асинхронной очереди. Но это ломается при `QUEUE_CONNECTION=sync` (тесты) или недоступности самой очереди при постановке job. Добавлен `SyncOrderToCrm::dispatchSafely()` — try/catch + `report()` вокруг `dispatch()`, используется везде вместо голого вызова. Подробности и как поймали — см. [[CRM интеграция]].

## predis вместо phpredis — независимость от pecl.php.net на билде

Реальный сбой на build-сервере Dokploy: `pecl install redis` не смог подключиться к `pecl.php.net:443` (сеть/файрвол окружения, не наш код — apk-пакеты через тот же build ставились нормально, только PECL недоступен). Вместо расширения (C, собирается на этапе `docker build`, требует сеть именно до `pecl.php.net`) — `predis/predis` через composer (чистый PHP, тянется вместе с остальными зависимостями с packagist, который явно доступен — `composer install` до этого всегда проходил). Компромисс — predis медленнее phpredis на больших объёмах, но для этого масштаба (один бот, не высоконагруженный сервис) разница не имеет значения, а независимость от ещё одного внешнего хоста на этапе сборки — имеет. Убрано из всех трёх Dockerfile (`Dockerfile`, `Dockerfile.prod`, `Dockerfile.dokploy`), `REDIS_CLIENT=predis` в `.env`/`.env.example`. Проверено вживую: `Redis::connection()->ping()` → `PONG`, полный набор тестов зелёный, образ `Dockerfile.dokploy` собирается и отвечает без единого упоминания `redis` в `php -m`.

## Polling вместо webhook — сеть блокирует Telegram в обе стороны

Реальная находка на том же деплое: после того как исходящие запросы до `api.telegram.org` заработали через прокси (см. ниже), `setWebhook` тоже прошёл успешно (домен/TLS/nginx/php-fpm — всё честно проверено: `curl` изнутри контейнера на сам вебхук-URL стабильно давал ожидаемый 403 без секрета). Но `getWebhookInfo` показывал растущий `pending_update_count` и `last_error_message: "Connection timed out"` — Telegram не мог достучаться ВХОДЯЩИМ соединением до сервера, хотя сервер сам достаёт исходящим (через прокси). Значит сеть блокирует Telegram в обе стороны независимо, не только "исходящее слепое пятно".

Решение — не чинить входящее (это вне нашего контроля, зависит от сети хостинга), а обойти его архитектурно: `telegram:poll` (long polling через `getUpdates`) требует только исходящих соединений, которые уже работают через прокси. Команда была помечена "только для локальной разработки" — на деле для этой сети она единственный рабочий вариант, не временная мера. См. `App\Console\Commands\TelegramPoll` — запускается третьим Application-ресурсом в Dokploy (без домена, сама снимает webhook при старте).

## TelegramClient: опциональный прокси до api.telegram.org

Реальный случай: с прод-хостинга (Dokploy-сервер) `setWebhook` падал с `cURL error 28: Connection timed out` — прямого сетевого доступа до `api.telegram.org` нет. В самом первом (несовпадающем с этим кодом) шаблоне переменных Dokploy были `TELEGRAM_PROXY_HOST/PORT/TYPE=SOCKS` — сначала отброшены как "код не читает", но оказались ровно тем, что нужно: кто-то до нас уже знал про эту проблему на этом хостинге.

`TelegramClient` теперь опционально заворачивает запросы в `Http::withOptions(['proxy' => ...])`, если заданы `TELEGRAM_PROXY_HOST`/`PORT` — `socks5h://` по умолчанию (резолвит DNS через сам прокси, не локально: локальный DNS может быть недоступен по той же причине, что и прямой выход). Пусто по умолчанию — прямое соединение, большинство хостингов эту проблему не имеют.

`Http::fake()` не даёt заглянуть в Guzzle-опцию `proxy` — тесты проверяют, что включение прокси в конфиге не ломает обычный вызов API (запрос идёт на правильный URL, отвечает как ожидается), не сам факт того, что cURL реально пойдёт через прокси — для этого нужен реальный прокси-сервер, недоступный в тестовом окружении.

**Дополнено**: добавлена поддержка логин/пароля (`TELEGRAM_PROXY_USERNAME`/`PASSWORD`) — публичные бесплатные прокси почти всегда требуют авторизацию. Учётные данные встраиваются в сам URL прокси как userinfo (`scheme://user:pass@host:port` — так cURL передаёт `Proxy-Authorization`), через `rawurlencode()` на случай спецсимволов в пароле (проверено тестом на `user@name`/`p@ss:word/1` — без экранирования `@`/`:`/`/` разъехались бы с разбором самого URL). Согласие пользователя на бесплатный публичный прокси — осознанный компромисс: токен бота идёт в URL каждого запроса к Telegram, а бесплатный прокси теоретически может его залогировать; предупреждён явно перед тем, как продолжить.

## resources/views: пустая папка не переживает git-клон

Реальный баг с деплоя: коммит "Убрать стоковую страницу Laravel" удалил единственный файл в `resources/views` (`welcome.blade.php`), оставив пустую директорию. Git не хранит пустые директории — они остаются на диске только там, где физически не были удалены (у меня локально, у Dokploy при свежем `git clone` — нет). `php artisan view:cache` падал с `Finder.php: The "/var/www/resources/views" directory does not exist`. Пойман `entrypoint.sh`'s `cache_or_warn` (не уронил контейнер), но кэш вьюх реально не работал.

**Почему ни одна локальная тестовая сборка это не поймала**: `docker build`/`COPY . .` берёт файлы с диска рабочей директории, не через git — пустая папка физически оставалась там с прошлого раза. Проверка на самом деле честно воспроизводящая деплой Dokploy — собрать образ из `git archive HEAD | tar -x` во временную директорию, не из рабочей копии. Взято на вооружение для дальнейших проверок деплой-путей.

Фикс — `.gitkeep` в `resources/views`. Backend без веб-интерфейса (см. README), реальных вьюх в папке нет и не планируется — файл нужен только чтобы директория существовала.

## sslip.io и HTTPS — предупреждение Dokploy оказалось ложным (в этом случае)

Dokploy при добавлении домена на `*.sslip.io` показывает предупреждение "does not support SSL/HTTPS, options will not have any effect". На практике Let's Encrypt всё равно выпустил рабочий, доверенный сертификат — `curl -sI https://.../up` без `-k` отдал чистый `HTTP/2 200` без единой ошибки сертификата. Не полагаться на это предупреждение как на истину в последней инстанции — проверять эмпирически. Для реального продакшна свой домен всё равно рекомендуется (см. README#Деплой-в-прод), но не потому, что sslip.io гарантированно не работает.

## entrypoint.sh: падение кэша не должно ронять контейнер

Реальный инцидент на Dokploy: `APP_URL` в Environment оказался битым (`https://` без хоста после схемы — воспроизведено локально, `php artisan config:cache` с таким значением кидает `Invalid URI`, Request.php:387). `entrypoint.sh` был написан с `set -e` без разбора команда за командой — падение `config:cache` валило весь скрипт, а с ним и весь контейнер, ещё до старта supervisor/php-fpm. Контейнер уходил в статус "exited" — и что хуже всего, в таком статусе в него нельзя зайти терминалом через UI Dokploy, чтобы вообще понять, в чём дело (сам инструмент диагностики недоступен ровно тогда, когда нужнее всего).

Исправлено: `cache_or_warn()` — если `config:cache`/`route:cache`/`view:cache` падает, громкое предупреждение в лог, но контейнер продолжает стартовать (приложение работает без кэша, медленнее, но работает и, главное, доступно для диагностики). Проверено вживую: тот же битый `APP_URL` — контейнер `Up`, не `Exited`, `/up` отвечает 200.

## Dokploy: один Dockerfile с supervisor, не Docker Compose

Реальный Dokploy пользователя оказался без типа ресурса "Compose" на Application — только Dockerfile/buildpacks, один контейнер на ресурс (выяснено по факту, при первом деплое: `docker-compose.dokploy.yml` некуда было подставить). Вместо трёх сервисов (app/nginx/queue) — `docker/php/Dockerfile.dokploy`: nginx + PHP-FPM в одном контейнере через supervisor (пакет `supervisor` из Alpine), очередь — второй Application-ресурс из того же образа с переопределённой командой запуска. `docker-compose.dokploy.yml`/`docker-compose.prod.yml` остались для голого сервера и на случай, если у Dokploy когда-нибудь найдётся Compose-ресурс — сам подход (PHP-FPM + nginx вместо artisan serve) не изменился, поменялся только способ упаковки в контейнеры.

Alpine-пакет `nginx` (не официальный образ `nginx:alpine`) подключает конфиги из `/etc/nginx/http.d/*.conf`, не `/etc/nginx/conf.d/*.conf` — проверено эмпирически (`docker run alpine apk add nginx` + `grep include`), не угадано по памяти о другом образе.

**Пойманный баг при стресс-тесте**: `supervisord`'s `startretries` по умолчанию — 3, после чего процесс уходит в FATAL и больше НИКОГДА не перезапускается сам, даже когда причина сбоя исчезла — нашли, намеренно убив php-fpm внутри контейнера и обнаружив, что он не восстановился (`/up` стабильно отвечал 502). Без этого теста баг вскрылся бы только в проде, на первом реальном падении процесса. Исправлено — `startretries=1000` на оба процесса (`docker/supervisor/supervisord.conf`), тот же принцип "пробовать почти всегда", что `restart: unless-stopped` на уровне docker-compose.

## nginx без ports: — совместимость с Dokploy

Деплой решено вести через [Dokploy](https://dokploy.com/) — у него свой Traefik держит 80/443 на хосте и сам оформляет TLS через Domains в UI. Публиковать `80:80` у nginx в `docker-compose.prod.yml` напрямую значило бы конфликтовать за тот же порт с самим Dokploy. Заменено на `expose: ["80"]` — сервис доступен другим контейнерам той же docker-сети (в том числе Traefik'у Dokploy) по имени `nginx:80`, без публикации на хост. Для деплоя БЕЗ Dokploy (голый сервер + Caddy/nginx-хоста) `ports: ["80:80"]` нужно вернуть — README#Деплой-в-прод это явно оговаривает.

## Прод: PHP-FPM + nginx, не artisan serve

Dev-образ (`docker/php/Dockerfile`) запускает `php artisan serve` — официально не для прода: однопоточный, сериализует все запросы, включая вебхуки от Telegram. Для прода — отдельный `docker-compose.prod.yml`/`Dockerfile.prod`: PHP-FPM за nginx (fastcgi_pass). Не Laravel Octane/Swoole — для соло-бизнеса с модестным потоком заказов лишняя сложность (stateful-приложение, память между запросами не сбрасывается сама, нужно следить за утечками), PHP-FPM — самый скучный и предсказуемый вариант, а не для этого масштаба экономить на процессах смысла нет. Проверено вживую (сборка, миграции, `/up` через nginx), не только описано.

## TLS — вне docker-compose.prod.yml

Certbot/Let's Encrypt внутрь compose-стека не завели: инициализация сертификата (webroot ACME challenge, до того как сертификат вообще есть) и его продление — отдельный процесс жизненного цикла, завязанный на конкретный домен/хостинг, о которых сам репозиторий ничего не знает. Стек отдаёт plain HTTP на 80; TLS-терминация — задача сервера, не приложения. В README дан один конкретный рецепт (Caddy, автоматический HTTPS в 3 строки конфига) как самый безболезненный вариант для соло-разработки, не единственный обязательный.

## Номер заказа без DB sequence

Изначально `orders.number` был `bigint` с дефолтом от Postgres `SEQUENCE` — красиво и правильно для прода, но `CREATE SEQUENCE` не существует в SQLite, на котором гоняются тесты. Не стали городить два разных пути для миграции (branch по `DB::getDriverName()`), просто перенесли генерацию в `Order::booted()` (`creating`-хук, `max(number) + 1`). Плата — теоретическая гонка при одновременном создании двух заказов (никогда не проверяли на реальной конкурентной нагрузке); при соло-разработке и небольшом потоке заказов это осознанно приемлемый риск, а не забытый баг. Если станет проблемой — вернуть Postgres-sequence с миграцией, специфичной для окружения.

## PendingInput как общий примитив

Причина отказа мастера "Другое" (ТЗ п.22) требует одного свободного текстового ответа вне сценария создания заявки. Вместо специальной таблицы под этот один случай — завели `pending_inputs` (`user_id` unique, `kind`, JSON `payload`, `expires_at`) как переиспользуемый примитив "жду один ответ по такому-то поводу". Оправдалось уже в Фазе 02 (шаги согласования цены). `order_drafts` — отдельная сущность, не унифицирована с `pending_inputs`, потому что там принципиально другая форма: заранее известная последовательность из 12+ шагов с типизированным enum, а не одноразовое ожидание.

## DateSlotPicker — вынесено на третьем использовании

Выбор "дата → слот" писался с нуля дважды: в `OrderDraftFlow` (Фаза 01, создание заявки) и в `OrderRescheduleFlow` (Фаза 02, перенос). Оба раза — осознанное дублирование (разные контексты, риск регрессии в уже протестированном коде). На третий раз (Фаза 03, планирование повторного визита в `OrderVisitFlow`) вынесли общий `DateSlotPicker`: рендер шагов + разбор "ДД.ММ" в одном месте. `OrderRescheduleFlow` отрефакторили на него, `OrderDraftFlow` — оставили как есть (не стали трогать проверенный код ради унификации). Дополнительный повод: именно в разборе даты жил баг с `Carbon::createFromFormat()` (см. [[Фаза 02 — Полевой цикл#Пойманные баги по пути]]) — одна точка вместо трёх снижает риск, что фикс в будущем попадёт не везде.

## TELEGRAM_MODE — health-check должен знать про polling

Пост-факт аудит после перехода на `telegram:poll` в проде (см. [[Решения#Polling вместо webhook — сеть блокирует Telegram в обе стороны]]) нашёл реальный баг: `system:health-check` (ТЗ п.104) безусловно дёргал `getWebhookInfo` и считал пустой `url` поломкой — а `telegram:poll` сам удаляет вебхук при старте, так что в polling-режиме пустой url это ожидаемое состояние, не авария. Без фикса это значило бы ложный алерт владельцу каждые 15 минут, навсегда. Исправлено: `TELEGRAM_MODE=webhook|polling` в конфиге (`config/services.php`), `SystemHealthCheck::checkWebhook()` полностью пропускает проверку вебхука при `polling`. Сознательно НЕ стали городить альтернативную проверку "жив ли процесс telegram:poll" — вне зоны видимости обычного HTTP/artisan-процесса без дополнительной инфраструктуры (heartbeat в БД/Redis), это отдельная задача, если понадобится.

## uploads.ini — PHP-лимиты загрузки отставали от лимита контроллера

Пост-факт аудит нашёл: `OrderMediaController` (Internal API, ТЗ п.88) разрешает файлы до 20 МБ и nginx подтверждён на 25 МБ (`client_max_body_size`), но ни один из трёх `Dockerfile` не переопределял PHP-дефолты `upload_max_filesize=2M`/`post_max_size=8M` — любой файл от CRM крупнее 2 МБ терялся бы PHP ещё до валидации Laravel, без внятной ошибки о размере. Не поймано раньше, потому что реальной CRM ещё нет (см. [[Открытые вопросы#Какая именно CRM]]) — никто не отправлял настоящий multipart-запрос крупнее пары КБ. Исправлено: `docker/php/uploads.ini` (`upload_max_filesize=25M`, `post_max_size=30M` — с запасом над лимитом контроллера, вровень с nginx), подключён во все три Dockerfile.

## QUEUE_CONNECTION=database — Redis не обязателен, пока нет реальной нагрузки

Пост-факт аудит прод-деплоя нашёл: в Environment реального Dokploy-приложения `REDIS_HOST`/`PASSWORD`/`PORT` оказались буквально незаполненными плейсхолдерами (`<Internal Host ресурса Redis>`) — отдельный Redis-ресурс для бота никогда не создавался, только `service-ops-db`. При этом реальный потребитель очереди — ровно один: `SyncOrderToCrm` (ТЗ п.87), а CRM ещё не подключена (`LogCrmAdapter`, см. [[Открытые вопросы#Какая именно CRM]]), и диспатч уже обёрнут в `dispatchSafely()` (безопасен при недоступной очереди). Поднимать инфраструктуру (ещё один ресурс в Dokploy) ради этого — решение без задачи. Переключили `QUEUE_CONNECTION` на `database` по умолчанию — таблица `jobs` уже смигрирована, работает поверх того же Postgres, отдельного сервиса не требует. `SystemHealthCheck::checkQueue()` теперь пингует Redis, только если `queue.default === 'redis'` — иначе эта проверка бессмысленна (проверяла бы не то, что реально используется). Redis (`predis`, см. [[Решения#predis вместо phpredis — независимость от pecl.php.net на билде]]) остаётся полностью поддержан кодом — переключить обратно, когда появится реальная CRM с заметным объёмом задач, это один env, без изменений кода.

## Таймаут HTTP-клиента vs long-polling — гонка валила контейнер telegram:poll

Первый реальный запуск `telegram:poll` третьим Application-ресурсом на Dokploy: контейнер стартовал ("Webhook удалён, слушаю апдейты"), но через один цикл падал в "exited". В логах — `cURL error 28: Operation timed out after 30001 milliseconds` на `getUpdates`. Причина: `getUpdates` в long-polling режиме просит Telegram держать соединение открытым до 30с (`'timeout' => 30`), а `TelegramClient::http()` использовал `Http::asJson()` без явного таймаута — то есть дефолтный таймаут Laravel, тоже ~30с. Гонка, которую клиент иногда проигрывает на миллисекунды раньше, чем Telegram успевает ответить пустым результатом. Хуже того, это исключение (`ConnectionException`, не HTTP-ошибка — ответа нет вообще, `$response->failed()` тут не сработал бы) никто не ловил: `while (true)` в `TelegramPoll::handle()` оборачивал в try/catch только обработку конкретного апдейта, не сам вызов `getUpdates`. Одна необработанная сетевая заминка убивала весь процесс (PID 1 в контейнере) → контейнер падал.

Не поймано раньше, потому что `telegram:poll` до этого момента ни разу не гонялся по-настоящему долго ни локально (там прямое соединение без прокси, быстрее), ни тем более в проде — переход на polling сам по себе состоялся только в этой сессии. Исправлено: `TelegramClient::http()` — явный `->timeout(35)` (с запасом над 30с long-poll); `TelegramPoll::handle()` — сетевой сбой на `getUpdates` теперь ловится, репортится и цикл продолжается с той же `offset` (апдейты не теряются) после паузы в 2с, а не роняет процесс.

## Escape-hatch из активного сценария — общий фикс, не патч одного flow

Живой QA-прогон 16.09.2026 нашёл тупик: на текстовом шаге черновика заявки (`OrderDraftFlow`) невалидный ввод (например нераспознаваемый телефон) заставлял бота повторять ошибку валидации даже на кнопку меню и на `/start` — `UpdateHandler::handleMessage()` проверял активный `OrderDraft`/`PendingInput` раньше команд, без исключений, и безусловно отдавал текст в обработчик сценария.

Не патчили только `OrderDraftFlow` — по конструкции `UpdateHandler` ровно та же безусловная проверка стоит перед ветвлением по `PendingInput->kind`, то есть тот же тупик воспроизводится на любом из восьми flow, использующих `PendingInput` (согласование цены, перенос, деталь, визит, отчёт, оплата, статистика, гарантия) — просто раньше никто не проверял их таким же образом руками. Фикс — на уровне диспетчера: `BotMenu::isMenuCommand()` (сверяет текст со сплющенным списком кнопок текущей роли, тот же источник, что рендерит клавиатуру, — не два места для синхронизации) плюс `UpdateHandler::exitActiveScenario()`, которые срабатывают раньше проверки черновика/pending на `/start` или любую кнопку меню: удаляют активное состояние, коротко уведомляют об отмене и отдают управление обычной командной диспетчеризации ниже — как если бы сценария не было вообще. Проверено тестом на обоих случаях (`OrderCreationFlowTest::test_menu_command_exits_stuck_draft_instead_of_repeating_validation_error`, `OrderDecisionFlowTest::test_menu_command_exits_stuck_pending_input_instead_of_being_swallowed_as_its_text`), не только на исходно найденном.

## «Назначена» vs «переназначена» — зависит от того, был ли у заявки мастер раньше

Тот же QA-прогон: `OrderNotifier::reassignedByAdmin()` всегда писал «переназначена», даже когда у заявки (`NEW`) раньше вообще не было мастера — переназначение по смыслу это только случай `MASTER_DECLINED` (мастер уже был, отказался, назначили другого). `OrderReassignFlow::assign()` фиксирует `$order->master_id !== null` до вызова `OrderStatusMachine::transition()` (тот перезаписывает `master_id`) — на `MASTER_DECLINED` это `true` (см. [[Статусы заказа]] — отказ не обнуляет `master_id`, тот остаётся на отказавшемся), на `NEW` — `false`. Флаг уходит в `OrderNotifier::reassignedByAdmin(..., bool $wasReassignment)`, который выбирает глагол.

## Достроены 7 заглушек меню — «Пользователи» не меняет роль

QA-прогон 16.09.2026 нашёл 7 из 12 кнопок меню на заглушке, хотя чек-лист 00-07 закрыт целиком — причина архитектурная (`BotMenu` завела полную клавиатуру ещё в Фазе 00, `UpdateHandler` подключал экраны только под пункты ТЗ, часть кнопок такого пункта не имела), не забытая задача. Достроены все 7 отдельным заходом: ADMIN — «Сегодня» (`OrderListScreens::today()`, `whereDate()`, не `where()` — visit_date хранится полным datetime по умолчанию для SQLite-грамматики date-cast, точное строковое сравнение никогда бы не совпало), «Поиск» (эвристика: ≤6 цифр — номер заявки, иначе — подстрока телефона; ТЗ формат не описывает), «Мастера» (плоский список, без per-item действия). MASTER — «Сегодня»/«Завтра» (тот же `whereDate()`, с явным исключением `MASTER_DECLINED` — `master_id` остаётся на отказавшемся мастере и после отказа, без исключения своя же отказанная заявка утекла бы обратно в «Сегодня»), «История» (`COMPLETED`/`PAID`, осознанное допущение — не любые терминальные).

«Пользователи» (SUPERADMIN, `UserManagementScreen`) — самая значимая находка QA-отчёта, но сознательно **не** даёт менять роль: список пользователей по ролям + вкл/выкл `is_active` уже существующим аккаунтам. Выдача ADMIN/SUPERADMIN остаётся ручным `tinker` — это не пробел, а тот же осознанный порог трения, что и в [[Решения#master:add без создания ADMIN/SUPERADMIN]], специально подтверждённый при планировании этого захода, а не унаследованный молча. Самодеактивация SUPERADMIN заблокирована отдельной проверкой (иначе можно было бы случайно отрезать себе доступ без возможности восстановить его иначе как через БД).

Визард «➕ Добавить мастера» (`MasterRegistrationFlow`) на том же экране дублирует поля и валидацию консольной `master:add` (telegram_id уникален, специализация обязательна ≥1, бренды/зоны опциональны) вместо вызова общего сервиса — второе использование той же логики, не третье, поэтому не выносим (см. [[Решения#DateSlotPicker — вынесено на третьем использовании]]). Создаёт только MASTER, симметрично тому, что сама `master:add` не создаёт ADMIN/SUPERADMIN.

## Перенос не меняет статус

ТЗ описывает `RESCHEDULED` как статус в общем списке, но граф переходов (п.15) даёт его двусмысленно ("ACCEPTED → ON_THE_WAY → RESCHEDULED"). Решили: перенос — это событие (меняются `visit_date`/`time_slot_label`), а не "заказ повис в состоянии RESCHEDULED, дальше берём его оттуда" — потому что дальше явно неоткуда брать (переход из RESCHEDULED никуда не описан). Решение: менять напрямую полями заказа + писать отдельную запись в `order_status_histories` с `old_status == new_status` и комментарием-описанием переноса, в обход `OrderStatusMachine::transition()` (это не транзиция состояния). `OrderStatus::RESCHEDULED` остаётся в enum как задокументированный неиспользуемый кейс — на случай, если позже понадобится показывать перенесённые заказы отдельным фильтром.
