# Гарантийный возврат

**Статус:** готово. Отложено в Фазе 03 ("P1, после запуска"), реализовано отдельным проходом по прямому запросу.

## Что в ТЗ (п.64-65)

- **п.64** — администратор: `[Создать гарантийное обращение]`. Поля (п.64.1): исходный order, проблема, дата, комментарий, мастер, новый слот.
- **п.64.2, связь** — `warranty_parent_order_id` на исходный заказ, стартовый статус `WARRANTY_RETURN`.
- **п.65, аналитика** — гарантийный повтор "не считается новым обычным коммерческим заказом", считать отдельно: `warranty_orders`, `warranty_rate`, `warranty_cost`.
- Побочные находки в ТЗ: `WARRANTY_RETURN` уже был в `OrderStatus` (заложен в Фазе 00), `warranty_parent_order_id`/`crm_id`/`lead_id` — в `orders.fillable` (Фаза 01), `OrderListScreens::CLOSED_OR_UNASSIGNED_STATUSES` уже исключал `WARRANTY_RETURN`, `StatsFlow` уже печатал `"Гарантийных: 0"` (буквальный ноль-заглушка) — везде задел был сделан заранее, просто не подключён.

## Что построено

- **`warranty_parent_order_id`** (nullable FK на `orders`) — гарантийное обращение это отдельная строка `Order`, не правка исходной. Поля клиента/техники/адреса копируются с родителя, не переспрашиваются (в п.64.1 их и нет в списке).
- **`WarrantyReturnFlow`** — визард на `PendingInput` (namespace `warranty`): проблема → комментарий (пропустить) → дата/слот (`DateSlotPicker`) → мастер (`MasterMatcher` по технике/бренду/зоне родителя, тот же список кандидатов, что видит `OrderReassignFlow`). Доступен только `isAdminLike()`.
- **`WARRANTY_RETURN → ASSIGNED`** в `OrderStatusMachine` — мастер и слот обязательны на входе (п.64.1), поэтому статус существует ровно миг между созданием и назначением, тот же паттерн, что `NEW` при создании через `OrderDraftFlow`. Дальше — тот же `OrderStatusMachine`, что у любого заказа: отдельного графа состояний для гарантии не потребовалось.
- **Кнопка "🔧 Гарантия"** — на карточке `orderCompleted` (кнопка живёт сколько угодно, Telegram не гасит inline-клавиатуры старых сообщений — гарантийный случай может всплыть неделями позже).
- **Статистика** (`OrderStatsCalculator`/`MasterStatsCalculator`) — `warranty_parent_order_id is not null` исключено из `new_orders`/`completed`/`revenue`/`avg_check` (и из per-master `assigned`/`accepted`/`declined` тоже — гарантийный визит не новое назначение с точки зрения бизнеса). Добавлены `warranty_orders`/`warranty_rate`/`warranty_cost` (admin) и `warranty` (per-master, подключено к уже существовавшей заглушке `"Гарантийных: 0"` в `StatsFlow`).
- **`OrderCardFormatter`** — карточка гарантийного заказа показывает `🔧 Гарантия по #NNNN`, чтобы мастер/админ сразу понимали контекст, не заглядывая в историю.
- **QA-сценарий 6** (ТЗ п.131) наконец реализован по-настоящему — полный визард через настоящий вебхук в `QaScenariosTest`, не заглушка. Заодно реализован и **сценарий 7** (CRM недоступна) — эта фича появилась раньше в этом же backlog-проходе, тест на неё просто ещё не был написан.

## Решение: WARRANTY_RETURN не отдельный граф состояний

Гарантийный заказ после назначения проходит ровно тот же `OrderStatusMachine`, что и обычный (`ACCEPTED → ON_THE_WAY → ... → COMPLETED → PAID`). ТЗ нигде не требует иного финансового или процессного поведения для гарантийного визита — только то, что он не должен искажать коммерческую статистику. Постройка отдельной state machine или ветвления "если гарантия — то..." внутри существующих flow (диагностика, отчёт, оплата) была бы решением без задачи.

## Формулы, которых ТЗ не даёт буквально (зафиксированы в коде)

- `warranty_rate` = `warranty_orders` (создано в периоде) / `completed` (обычных завершённых в тот же период) × 100.
- `warranty_cost` = `parts_cost` + `master_payout` по завершённым гарантийным заказам за период — не `final_price` (гарантийный ремонт обычно бесплатен клиенту, себестоимость для бизнеса считается через фактические расходы, не выручку).

## Осознанно не сделано

- **Internal API не тронут** — ТЗ п.88 не включает гарантию в список из 12 эндпоинтов; это чисто ADMIN-действие внутри бота.
- **Не предзаполняется мастер исходного заказа** — `MasterMatcher` показывает тот же список кандидатов, что и при обычном переназначении; исходный мастер там есть, но не выделен принудительно. ТЗ этого не требует, а предвыбор мог бы создать неверное впечатление, что гарантию обязан закрывать тот же человек.
