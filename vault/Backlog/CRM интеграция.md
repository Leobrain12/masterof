# CRM интеграция

**Статус:** архитектура и Internal API готовы, реального адаптера под конкретную CRM ещё нет — и не обязательно понадобится по документации. **Не часть исходного чек-листа 00-07** — первый backlog-пункт, взятый в работу после его закрытия.

## Что нашлось в ТЗ, когда реально понадобилось

К этому моменту исходный текст ТЗ (docx) выпал из контекста — пережили сжатия разговора только код и заметки в `vault/`, а про CRM записей не было, потому что раньше не было повода. Пришлось поднимать текст из журнала сессии (`~/.claude/projects/.../*.jsonl`, там остался результат первого чтения docx). См. пояснение пользователю в разговоре — сам факт этого процесса стоит держать в голове: то, что не попало в `vault/` или код, не переживает следующий разрыв контекста.

ТЗ (п.85-90, п.120, п.129) оказалось конкретнее, чем казалось по единственному упоминанию "появится в фазе CRM" (Фаза 01):
- **CRMAdapter** — абстракция, `Bitrix24CRMAdapter` дан как пример названия класса, не как обязательный выбор конкретной CRM.
- **п.85.1** — Telegram-хендлеры не должны напрямую дёргать CRM: `Backend → DB → Queue → CRMAdapter`.
- **п.87, "CRM outage"** — заказ продолжает работать, если CRM недоступна; синк уходит в очередь и ретраится автоматически. **CRM не является single point of failure.**
- **п.88** — минимальный набор из 12 Internal API эндпоинтов (`/transition` уже был построен в Фазе 01).

## Что построено

- **12 Internal API эндпоинтов** (`app/Http/Controllers/Api`) — `POST/GET/PATCH /orders`, `/orders/search`, `/assign`, `/visits`, `/work-report`, `/media`, `/payments`, `/masters`, `/masters/{id}/stats`, `/stats`. Каждый write-эндпоинт зеркалит соответствующий бот-flow (`OrderVisitFlow`, `WorkReportFlow`, `PaymentFlow`, `OrderReassignFlow`) — те же правила целостности (final_price считается, не принимается; visit закрывается тем же способом), просто без Telegram/PendingInput-обвязки вокруг.
- **`OrderResource`** — общий JSON-формат заказа, один на все read/write эндпоинты, чтобы CRM не разбирала разные формы ответа от разных вызовов.
- **`CrmAdapter`** (интерфейс) + **`LogCrmAdapter`** (реализация по умолчанию — логирует снимок заказа, ничего никуда не шлёт, никогда не бросает). Подключается через `CRM_ADAPTER_CLASS` в `.env`.
- **`SyncOrderToCrm`** (job) — `$tries=5`, `backoff()` до 30 минут. Единственная точка запуска — `OrderStatusMachine::transition()`: любой флоу, меняющий статус (приём, диагностика, отчёт, оплата...), уже проходит через неё, отдельно дёргать синк не нужно. Плюс явный вызов в `OrderController::store/update`, потому что создание/правка заказа не всегда сопровождается сменой статуса.
- **`orders.lead_id`/`crm_id`/`source`** — колонки существовали с Фазы 01 (кто-то, то есть я тогда же, заложил их заранее под это), просто не были ничем заполнены до сих пор.
- **`orders.created_by` стал nullable** — заказ через API не привязан к telegram-пользователю, симметрично уже существовавшему `OrderStatusHistory.changed_by_user_id` (см. `OrderTransitionController`, `actor: null`).

## Решение: dispatchSafely() — почему не просто положиться на очередь

`SyncOrderToCrm::dispatch()` в проде на Redis сам по себе неблокирующий и не бросает исключений — казалось бы, п.87 ("CRM не SPOF") соблюдается автоматически просто по природе асинхронной очереди. Но это не держится безусловно: с `QUEUE_CONNECTION=sync` (как в тестах) `dispatch()` выполняет job **синхронно** — падение адаптера бросает исключение прямо в `OrderStatusMachine::transition()`, ломая сам переход заказа. То же может произойти в проде, если Redis недоступен даже для постановки в очередь (не только для её обработки).

Добавлен `SyncOrderToCrm::dispatchSafely()` — статический метод, оборачивающий `dispatch()` в try/catch с `report()`. Используется во всех трёх местах вызова вместо голого `::dispatch()`. Проверено тестом (`CrmSyncTest::test_crm_outage_does_not_break_order_transition`) — без этой обёртки тест падает, с ней заказ реально меняет статус в БД, даже когда адаптер гарантированно бросает исключение на каждый вызов.

## Осознанные упрощения

- **Заказ через API создаётся без мастера** (status=NEW, Visit #1 без master_id) — назначение отдельным вызовом `/assign`, либо ADMIN подбирает вручную в боте через уже существующий экран «Нераспределённые» (`OrderListScreens`) и `OrderReassignFlow`. Ничего нового строить не пришлось — этот путь был готов с Фазы 01, просто ни разу не использовался (заявка из бота сразу создаётся с мастером за один диалог).
- **Медиа через API — обычный multipart-файл**, не `telegram_file_id`. `order_media.telegram_file_id`/`uploaded_by_user_id` стали nullable для этого случая (миграция `2026_09_15_120500`).
- **ADMIN/SUPERADMIN не заводятся через API** — только MASTER (через `master:add`, см. Фазу 07) и то не отсюда. Не требовалось ТЗ, не строили.
- **`GET /orders/search` без курсорной пагинации** — обычный `paginate()`, для ожидаемого объёма (один сервис, не маркетплейс) этого достаточно.
