# Схема данных

## Идентификаторы

Все основные сущности (`User`, `Master`, `Order`, `OrderStatusHistory`, `OrderDraft`, `PendingInput`) — UUID первичный ключ (`HasUuids`). Справочники (`ApplianceType`, `Brand`, `GeoZone`, `TimeSlot`, `Symptom`) — обычный автоинкремент, они простые и внешние системы на них не ссылаются напрямую.

`Order.number` — отдельный человекочитаемый bigint (`#4217`), не PK. Генерируется в `Order::booted()` (`creating`-хук) как `max(number) + 1`, **не** через БД-последовательность — см. [[Решения#Номер заказа без DB sequence]].

## Основные таблицы (после Фазы 01)

- **users** — `telegram_user_id` (уникальный, единственный идентификатор для авторизации), `role` (enum [[Роли и права|UserRole]]), `is_active`.
- **masters** — 1:1 с `users`. `status` (enum `MasterStatus`: ACTIVE/DAY_OFF/VACATION/DISABLED — на назначение годятся только первые два, см. `Master::isAssignable()`). Связан many-to-many с `appliance_types`, `brands`, `geo_zones` через pivot-таблицы `master_appliance_type`, `master_brand`, `master_geo_zone`.
- **orders** — см. [[Статусы заказа]] для state machine. Хранит и снапшот времени слота (`time_slot_label`, на случай кастомного "Другое"), и опциональную ссылку на справочник (`time_slot_id`). Поля `failure_reason`/`work_needed`/`labor_price` (Фаза 02) и `part_*` (Фаза 03) — "текущее состояние" заказа, не история: живут прямо на Order, а не в дочерних сущностях, потому что в любой момент актуален только один активный кейс (см. [[Решения]]).
- **order_status_histories** — append-only лог смены статуса. Пишется только через `OrderStatusMachine::transition()`, больше нигде.
- **order_drafts** — server-side состояние сценария создания заявки. Один черновик на пользователя (`unique(created_by_user_id)`), с `expires_at` (таймаут 30 минут).
- **pending_inputs** — общий примитив "жду один кусок текста/шаг от этого пользователя по такому-то поводу" (`kind` + JSON `payload`). Возник для причины отказа "Другое", переиспользуется в Фазах 02-05 (согласование цены, перенос, заявка на деталь, планирование визита, отчёт, приём медиа). См. [[Решения#PendingInput как общий примитив]].
- **contact_attempts** — попытки дозвона (Фаза 02), append-only, без FK на статус заказа.
- **order_visits** — визиты в рамках заказа (Фаза 03). `status` только `SCHEDULED`/`COMPLETED` — не дублирует детальные статусы Order, см. [[Фаза 03 — Визиты и детали#OrderVisit.status — сознательно не вторая state machine]]. Visit #1 создаётся автоматически при создании заказа, закрывается либо при планировании следующего визита, либо при подтверждении WorkReport (Фаза 04).
- **work_reports** — финальный отчёт о ремонте (Фаза 04), отдельная сущность, не поля на Order (в отличие от предварительных failure_reason/work_needed/labor_price из Фазы 02 — см. выше). Создаётся один раз, при подтверждении, дальше не редактируется.
- **order_media** — фото/видео (Фаза 05), универсальная сущность на все стадии (`stage`: BEFORE/DIAGNOSTICS/DURING/AFTER/PART/OTHER). `storage_path` указывает в приватный диск `media` (см. [[Стек и инфраструктура]]), `telegram_file_id` — для мгновенной переотправки в чат без похода в хранилище.

## Справочники

`appliance_types`, `brands`, `geo_zones`, `time_slots`, `symptoms` — управляются только сидером (`ReferenceDataSeeder`), в боте нет админ-экрана редактирования справочников (не входит ни в один пункт чек-листа явно; если понадобится — это кандидат в бэклог).

## Диаграмма связей (упрощённо)

```
User 1—1 Master ⟷ (M:N) ApplianceType / Brand / GeoZone
Order → ApplianceType, Brand?, GeoZone?, TimeSlot?, Master?, User(created_by)
Order 1—N OrderStatusHistory
User 1—1 OrderDraft (пока активен)
User 1—1 PendingInput (пока активен)
```
