# Статусы заказа

Полный набор статусов объявлен в `App\Enums\OrderStatus` — все 18 значений из ТЗ сразу, потому что это просто список имён. А вот **допустимые переходы между ними живут отдельно**, в `App\Services\Orders\OrderStatusMachine::ALLOWED`, и заполняются только тогда, когда экран, вызывающий этот переход, реально построен. Никогда не угадывать переход заранее — легко ошибиться в семантике, которая станет ясна только при реализации экрана.

## Единственная точка входа

`OrderStatusMachine::transition()` — единственное место, где меняется `orders.status`. Внутри:

1. `SELECT ... FOR UPDATE` (на Postgres — реальная блокировка строки; на sqlite в тестах — no-op, но это ОК, там нет параллелизма).
2. Проверка `ALLOWED[текущий_статус]` содержит целевой.
3. Если да — сохраняет доп. атрибуты (например `master_id` при переходе в ASSIGNED), меняет статус, пишет `OrderStatusHistory`.
4. Если нет — кидает `InvalidOrderTransitionException`, которую вызывающий код превращает в понятное сообщение "Заявка уже изменена администратором. Обновите список заказов." (ТЗ п.112 — конкурентные действия).

Это касается и Internal API (`POST /orders/{id}/transition`) — контроллер тоже просто вызывает `OrderStatusMachine`, отдельной логики валидации переходов в контроллере нет.

## Граф переходов по состоянию на конец Фазы 04

```
NEW → ASSIGNED
ASSIGNED → ACCEPTED | MASTER_DECLINED
MASTER_DECLINED → ASSIGNED        (переназначение другому мастеру)
ACCEPTED → ON_THE_WAY | NO_CONTACT
ON_THE_WAY → ARRIVED | NO_CONTACT
ARRIVED → DIAGNOSTICS
DIAGNOSTICS → PRICE_APPROVAL | WAITING_PART | UNREPAIRABLE | CUSTOMER_CANCELLED
PRICE_APPROVAL → IN_PROGRESS | CUSTOMER_CANCELLED
WAITING_PART → ACCEPTED           (визит запланирован, см. Фаза 03)
IN_PROGRESS → COMPLETED
COMPLETED → PAID
```

Актуальный источник истины — таблица `ALLOWED` в коде, эта схема просто снимок; обновляй её вместе с фазой, которая меняет граф.

## Статусы, для которых пока нет UI
