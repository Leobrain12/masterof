# Роли и права

## Роли

`App\Enums\UserRole`: `SUPERADMIN`, `ADMIN`, `MASTER`. `isAdminLike()` = SUPERADMIN или ADMIN — используется везде, где по смыслу "любой админ", а не конкретно суперадмин (создание заявок, списки заказов, переназначение мастера).

Разница SUPERADMIN/ADMIN пока чисто в меню бота (кнопка "Пользователи" видна только SUPERADMIN, [[Фаза 00 — Фундамент|BotMenu]]) — отдельных прав на уровне сервисов ещё нет, экран управления пользователями не построен ни в одной фазе пока.

## Авторизация

Единственный идентификатор — `telegram_user_id`. **Никогда** не username (может смениться). Неизвестный `telegram_user_id` получает фиксированный ответ и не создаёт аккаунт сам — доступ выдаётся только вручную через сидер/будущий экран "Пользователи".

Проверка происходит не через классический Laravel-guard (`auth()->user()`), а вручную в `UpdateHandler::handle()` на каждый апдейт — потому что "запрос" здесь не HTTP-запрос конкретного пользователя, а вебхук Telegram с апдейтом внутри, и юзера нужно достать из тела апдейта (`message.from.id` / `callback_query.from.id`).

## Object-level permission

Каждый flow, где это важно, проверяет владение объектом на уровне данных, а не полагается на то, что кнопку видел "только тот, кому надо":

- `OrderDecisionFlow::findAssignedOrder()` — мастер не может принять/отклонить чужую заявку, даже подставив чужой номер в callback (ТЗ п.92).
- Reassign/список screens — доступны только `isAdminLike()`, при этом фактическая проверка — по роли пользователя, приславшего апдейт, а не по тому, кому изначально отправили сообщение с кнопкой.
