# Фаза 07 — Прод-готовность

**Статус:** готово — последняя фаза чек-листа. **Цель:** не страшно пустить в систему реальный поток заказов и реальные деньги.

## Что построено

- **Idempotency по `telegram_update_id`** (ТЗ п.90) — таблица `telegram_updates` с `update_id` как PK, `TelegramUpdate::claim()` атомарно "занимает" апдейт через `insertOrIgnore`; повторная доставка тихо выходит в первой же строке `UpdateHandler::handle()`, до всей бизнес-логики. Не check-then-insert (гонка), а сама уникальность БД как барьер.
- **10 QA-сценариев из ТЗ п.131** (`tests/Feature/QaScenariosTest.php`) — по одному тесту на сценарий, через настоящий webhook-эндпоинт, а не напрямую сервисы. 8 из 10 реализуемы и зелёные; 2 (гарантийный возврат, CRM недоступна) физически нечем тестировать — фичи не построены, тест появится вместе с ними, не раньше.
- **Аудит object-level permission** (`tests/Feature/ObjectPermissionAuditTest.php`) — систематический прогон "чужой мастер" по каждому flow, использующему `MasterOrderGuard` (10 штук), не только по самым очевидным accept/decline. Все прошли с первого раза — начиная с Фазы 02 каждый новый flow сразу строился поверх guard'а, здесь просто подтверждено, что нигде не забыли.
- **db:backup / db:restore** — дамп с `--clean --if-exists`, поэтому restore безопасно гонять поверх текущей базы: именно так и протестирован (снял бэкап дев-базы → восстановил на себя же). Запланирован на 03:00 через `routes/console.php`.
- **system:health-check** — вебхук (застрявшие ошибки, размер очереди Telegram), Redis, БД; алерт `TELEGRAM_OWNER_ID` в Telegram при проблеме, репорт в Sentry если настроен. Каждые 15 минут.
- **Sentry** (`sentry/sentry-laravel`) — установлен и подключён в `bootstrap/app.php`, но `SENTRY_LARAVEL_DSN` пуст по умолчанию: без него SDK ничего никуда не шлёт, включать по факту готовности к проду.
- **HTTPS-проверка** в `telegram:webhook set` — отказ сразу с понятной ошибкой, а не после невнятного ответа Bot API.
- **Прод-чеклист** в README — то, что нельзя проверить кодом (флаги окружения, cron, юридическое согласование ПД) сведено в один список перед реальным запуском.

## Пойманные баги

Оба — в новом коде этой же фазы, не наследие:

1. **`pg_dump`/`pg_restore` версии 18 против сервера Postgres 16.** Alpine-пакет `postgresql-client` (generic) тянет последнюю доступную мажорную версию клиента — на момент разработки 18, а `db`-сервис в `docker-compose.yml` — `postgres:16-alpine`. `pg_dump` от 18-го клиента пишет в дамп `SET transaction_timeout = 0;` — параметр, которого в Postgres 16 не существует, и `psql --set ON_ERROR_STOP=1` обрывает восстановление. Не поймал бы это без реального прогона `db:restore` — на бумаге "клиент есть, значит работает". Исправлено: `postgresql16-client` вместо generic-пакета, с комментарием в Dockerfile держать версию клиента синхронной с тегом образа `db`.
2. **`Carbon::diffInMinutes()` без `absolute: true` возвращает знаковую разницу.** В используемой версии Carbon (3.x) `$a->diffInMinutes($b)` по умолчанию отрицательна, если `$b` раньше `$a` — не абсолютное значение, как было в Carbon 2. `system:health-check` из-за этого считал ошибку вебхука трёхчасовой давности "недавней" (`-180 <= 15` истинно). Пойман собственным тестом (`old_webhook_error_does_not_trigger_alert`), не постфактум.

## Отложено осознанно

- **Маскирование телефона/адреса в логах** (ТЗ п.103) — аудит (`grep` по всем `Log::`/`report(` в `app/`) не нашёл ни одного места, где телефон или адрес клиента попадают в лог: исключения либо системные (БД/Redis/HTTP-уровень), либо ссылаются на заказ только по номеру (`#4217`), не по содержимому. Строить утилиту маскирования под риск, которого нет в коде, — то самое "решение без задачи". Конвенция на будущее: логировать/репортить только `order->code()`/ID, никогда сырые `customer_phone`/`address`, — если появится реальное место с этим риском, маскировать тогда же, не раньше.

## Пост-фактум аудит (09.09.2026) и что было закрыто сразу

Отдельный проход после закрытия фазы нашёл два пункта, которые сама фаза не покрывала:

- **Нет способа завести мастера без tinker/SQL** — закрыто командой `master:add` (см. [[Решения#master:add без создания ADMIN/SUPERADMIN]]).
- **Ни одного коммита в git** — закрыто 09.09.2026: первый коммит, приватный репозиторий на GitHub (`github.com/Leobrain12/masterof`).
- **Стоковая страница Laravel на `/`** — закрыто 15.09.2026: маршрут и `welcome.blade.php` удалены, `/` теперь честный 404 (интерфейс — только бот, `/up` для health-check не трогали).
- **Нет rate limiting на вебхуке/internal API** — закрыто 15.09.2026: `throttle:telegram-webhook` (300/мин по IP) и `throttle:internal-api` (60/мин по `X-Internal-Api-Key`), оба стоят первым middleware — режут объём до проверки секрета/ключа. См. [[Решения#Rate limiting — throttle до аутентификации, не после]].

- **Нет prune для `telegram_updates`/`pending_inputs`/`order_drafts`** — закрыто 15.09.2026: все три модели используют `Illuminate\Database\Eloquent\Prunable` (истёкшее по `expires_at` для pending_inputs/order_drafts, `processed_at` старше 7 дней для telegram_updates), `model:prune` подхватывает их автообнаружением и запланирован ежедневно в 03:15, сразу после `db:backup`.

Все пункты пост-фактум аудита закрыты.

## Прод-контур Docker (15.09.2026)

Отдельный проход "подготовиться к выкладке в прод" нашёл, что `docker-compose.yml` в принципе не годится для прода — не пункт чеклиста, а сам способ его исполнить: `artisan serve`, код томом, БД/Redis портами наружу. Построен `docker-compose.prod.yml` + `docker/php/Dockerfile.prod` (PHP-FPM) + `docker/nginx` — детали и почему не Octane/Swoole см. [[Решения#Прод PHP-FPM + nginx, не artisan serve]]. TLS сознательно не внутри compose — см. [[Решения#TLS — вне docker-compose.prod.yml]].

Проверено вживую под отдельным compose-проектом (`-p service_ops_prod`), не только собрано: сборка образа, поднятие всего стека, `migrate --force` на чистую БД, `/up` через nginx → 200, `/` → 404, вебхук без секрета → 403, opcache загружен. Нашёлся реальный порядок-зависимый нюанс: если `queue`/`app` стартуют раньше первой миграции, лог ловит безвредную `relation "cache" does not exist` (CACHE_STORE=database) на первый опрос — задокументирован порядок в README (db+redis → migrate → остальное).

Полный деплой-рантбук — README#Деплой-в-прод.
