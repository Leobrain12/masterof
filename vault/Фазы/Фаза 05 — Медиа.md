# Фаза 05 — Медиа

**Статус:** готово, 63/63 теста по проекту. **Цель:** фото/видео ремонта хранятся у нас, а не только в переписке с мастером, и есть чем их посмотреть.

## Что построено

- **OrderMedia** (ТЗ п.49) — универсальная сущность вместо отдельной WorkReportPhoto, как и требует ТЗ. `stage` (BEFORE/DIAGNOSTICS/DURING/AFTER/PART/OTHER), `media_type` (PHOTO/VIDEO), опциональные `visit_id`/`work_report_id`.
- **TelegramClient::downloadFile()** — скачивание по `file_id` через `getFile` + прямой GET на `api.telegram.org/file/...`. Лимит 20 МБ на видео проверяется **до** скачивания, по `file_size` из самого апдейта — не тратим запрос на файл, который всё равно не влезет.
- **MediaCollector** — общий сервис "принять один файл, скачать, сохранить, ответить счётчиком", переиспользуется тремя входами:
  1. `PartRequestFlow` — фото/видео детали (stage=PART), необязательный шаг, был отложен с [[Фаза 03 — Визиты и детали]].
  2. `WorkReportFlow` — фото/видео ремонта (stage=AFTER) перед подтверждением отчёта, был отложен с [[Фаза 04 — Отчёт и деньги]]. Медиа собираются раньше, чем создаётся `WorkReport` (id ещё нет) — привязка `work_report_id` идёт задним числом в `confirm()`.
  3. `MediaCollectionFlow` — самостоятельная кнопка "📷 Добавить медиа" на IN_PROGRESS (stage=DURING), не привязана ни к какому другому сценарию.
- **Диск `media`** (`config/filesystems.php`) — локальная приватная папка в разработке, в проде переключается на S3-совместимое хранилище в РФ через один env (`MEDIA_DISK_DRIVER=s3` + `AWS_*`), без изменений в коде. См. [[Стек и инфраструктура]].
- **MediaViewer** — просмотр медиа переотправкой через сам Telegram по сохранённому `telegram_file_id`, не через хранилище (см. решение ниже). Кнопка "🖼 Медиа" появляется на карточках заказа (и у мастера, и у админа), когда у заказа есть хоть один файл.

## Решение: альбомы не требуют специальной обработки

ТЗ п.53 требует обрабатывать каждый файл альбома, а не только первый. Специального кода под `media_group_id` нет и не понадобилось: Telegram присылает каждое фото альбома отдельным апдейтом, а пока вызывающий сценарий (PendingInput) остаётся в состоянии приёма медиа, каждый такой апдейт долетает до `MediaCollector` как обычно. Единственное, что было важно — **не выходить** из состояния приёма после первого файла, что и так было архитектурным свойством PendingInput-сценариев. Проверено тестом с последовательностью из трёх фото.

## Решение: просмотр через Telegram, не через signed URL

`OrderMedia::signedUrl()` реализован (через `Storage::disk('media')->temporaryUrl()`), но реально просмотр в боте идёт через переотправку файла по `telegram_file_id` — мгновенно, файл уже на серверах Telegram, скачивать из своего хранилища не нужно. Приватное хранилище (ТЗ п.54, 99) существует не для показа внутри бота, а для надёжности и соответствия 152-ФЗ: копия должна быть не только у Telegram. `signedUrl()` пригодится, когда (если) появится веб-интерфейс — на локальном диске `temporaryUrl()` недоступен (ограничение адаптера), поэтому метод возвращает `null` в разработке — это ожидаемо, не баг.

## Осталось наблюдение, не про медиа

Список "Активные" (`OrderListScreens::active()`) до сих пор показывает только ASSIGNED/ACCEPTED — с фазы 01, когда это были единственные достижимые статусы. Сейчас заказ большую часть жизни проводит в других статусах (DIAGNOSTICS, WAITING_PART, IN_PROGRESS, COMPLETED...), и админский обзор их не видит. Не чинил в этой фазе — не про медиа, но стоит поднять в [[Открытые вопросы]] как кандидата на Фазу 06.
