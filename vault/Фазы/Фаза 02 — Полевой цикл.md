# Фаза 02 — Полевой цикл

**Статус:** готово, 39/39 тестов зелёные (весь проект). **Цель:** мастер проводит заказ от выезда до начала ремонта, перенос и недозвон работают, отказ клиента на согласовании цены обязателен с причиной.

## Что построено

- **Граф переходов** пополнен: `ACCEPTED→ON_THE_WAY→ARRIVED→DIAGNOSTICS`, дальше ветвление `DIAGNOSTICS→{PRICE_APPROVAL, WAITING_PART, UNREPAIRABLE, CUSTOMER_CANCELLED}`, `PRICE_APPROVAL→{IN_PROGRESS, CUSTOMER_CANCELLED}`. См. [[Статусы заказа]].
- **MasterOrderScreen** — единый экран активной заявки мастера («Мои активные»): один и тот же рендер карточки, набор кнопок зависит от текущего статуса. Реализация DoD-требования "один экран, а не разные сущности под каждый статус" (UI-ТЗ п.4).
- **DiagnosisFlow** — 4-way ветвление результата диагностики. "Нужна деталь" и "Ремонт нецелесообразен" тут — только смена статуса с комментарием; подробные поля (артикул, закупочная цена, фото) — фаза 03.
- **PriceApprovalFlow** — причина неисправности → работы → цена работ → цена запчастей → показ итога → решение клиента (согласился/отказался, у отказа — обязательная причина). Multi-step ввод через `PendingInput` (kind=`price_approval`), решение клиента — через `kind=price_decline_reason` с тем же паттерном "Другое → свободный текст", что и в [[Фаза 01 — Заказы|отказе мастера]].
- **ContactAttemptFlow** — недозвон, 5 причин (ТЗ п.37), порог эскалации в NO_CONTACT — константа `3`, не настройка (см. [[Открытые вопросы#max_contact_attempts и другие settings]]).
- **OrderRescheduleFlow** — перенос с новой датой/слотом/причиной. Не проходит через `OrderStatusMachine` — см. [[Решения#Перенос не меняет статус]].
- **MasterOrderGuard** — вынесенная общая проверка владения заявкой, теперь используется и `OrderDecisionFlow` (рефакторинг заодно почистил дублирование из Фазы 01).

## Пойманные баги по пути

- **`Carbon::createFromFormat()` кидает исключение, а не возвращает `false`**, когда формат не может быть разобран из-за нехватки данных (например `'d.m.Y'` против ввода без года). Код был написан в расчёте на `false` (стандартное поведение для *успешного* разбора с недостающими полями), но при откровенно нехватающих данных Carbon 3 бросает `InvalidFormatException` (наследник `\InvalidArgumentException`). Баг жил и в `OrderDraftFlow` с Фазы 01 незамеченным — там ветка "Выбрать дату" ни разу не тестировалась текстом. Нашли через тест переноса с кастомной датой, пофиксили в обоих местах (`try/catch` вокруг `createFromFormat`), и заодно добавили недостающий тест на кастомную дату в создании заявки.
- Рефакторинг `OrderDecisionFlow` на общий `MasterOrderGuard` слегка изменил текст сообщения при гонке статусов ("уже изменена администратором" → "уже изменена. Обновите список заказов.") — осознанно, не баг: сообщение теперь общее для всех flow, а не только для админ-инициированных изменений. Тест поправлен.

## Осознанные упрощения

- "Нужна деталь"/"Ремонт нецелесообразен" на диагностике не запрашивают у мастера комментарий — сразу переход со стандартной пометкой. Полноценный сбор данных о детали — фаза 03.
- Отказ клиента *на диагностике* (до показа цены) не имеет отдельного списка причин, в отличие от отказа *после* согласования цены (там 5 причин из ТЗ п.31) — потому что сам ТЗ для этой точки список причин не даёт.
- Кнопка "Позвонить клиенту" из Figma-макета не реализована как отдельная кнопка — номер телефона и так есть в тексте карточки заказа.
